Arquitectura de un sistema web para la gestión de pedidos de una cafetería

1. Introducción

Café Express es una cafetería que registra sus pedidos de forma manual, lo que genera errores de transcripción, pérdida de comprobantes y desconocimiento, por parte del cliente, del estado de su pedido. Este documento presenta el diseño arquitectónico y el prototipo funcional de un sistema web pequeño para gestionar dichos pedidos.

El trabajo siguió seis pasos: (1) análisis de requisitos funcionales y no funcionales; (2) diseño arquitectónico mediante cuatro diagramas UML; (3) investigación y selección de patrones de diseño, incluyendo su pertinencia en entornos de computación en la nube; (4) construcción de un prototipo funcional que evidencia los patrones seleccionados; (5) preparación de la presentación; y (6) este informe.

La decisión central de arquitectura es la separación de responsabilidades: una arquitectura por capas bajo el esquema Modelo-Vista-Controlador, donde cada componente tiene una única responsabilidad y se comunica solo con las capas adyacentes. Esta decisión responde simultáneamente a los requisitos no funcionales del sistema: facilidad de uso, protección de la información, mantenibilidad, extensibilidad y escalabilidad.

2. Análisis de requisitos

2.1 Técnica de análisis

Se aplicó la observación del proceso actual (pedidos en papel) junto con la técnica de eventos y actores: identificados los actores (cliente y administrador), se listaron los eventos del negocio que ellos disparan y de cada evento se derivó un requisito funcional.

2.2 Requisitos funcionales

IDRequisitoActorDescripción
RF-01Consultar los productosCliente El sistema muestra nombre, categoría, precio y disponibilidad de cada producto.
RF-02Realizar los pedidosCliente Selecciona productos y cantidades, indica nombre y forma de pago; el sistema valida reglas y registra el pedido.
RF-03Consultar el estado del pedidoCliente Con el número de pedido consulta estado actual, detalle y totales.
RF-04Consultar los pedidosAdministrador Lista todos los pedidos con cliente, estado y valores.
RF-05Actualizar el estado del pedidoAdministrador Solo transiciones válidas: RECIBIDO → EN_PREPARACION → LISTO → ENTREGADO, o CANCELADO.
RF-06Gestionar productosAdministrador Crear, editar precio, habilitar/deshabilitar y eliminar productos.

2.3 Requisitos no funcionales y su respuesta arquitectónica

IDRequisitoDecisión arquitectónica que lo satisface
RNF-01Fácil de utilizar Interfaz web de una sola página con tres pestañas (Menú, Mi pedido, Administración); API REST coherente.
RNF-02Proteger la información Verificación de credenciales en un único punto (controladores) con token X-Admin-Token; evolución prevista hacia Identity Server (OAuth2/JWT).
RNF-03Fácil de mantener Capas MVC + patrón Repositorio: módulos pequeños con responsabilidad única.
RNF-04Agregar funcionalidades Interfaces e inyección de dependencias: nuevos comportamientos sin reescribir código existente.
RNF-05Escalabilidad Contenedor Docker sin dependencias nativas: escala verticalmente (más recursos al nodo) u horizontalmente (réplicas/pods detrás de balanceador de carga).

4. Patrones de diseño seleccionados

Se investigaron los catálogos clásicos (Gamma et al., 1994; Fowler, 2002) y los patrones para la nube (Microsoft, 2024). La selección y los descartes se justifican a continuación.

PatrónDecisiónJustificación
MVC (capas)Seleccionado Vista (static/), controladores (controller/) y modelo/servicio (service/, domain/) separados; responde directamente a RNF-03 y evita el antipatrón de lógica, interfaz y datos mezclados en un solo bloque.
RepositorySeleccionado Los servicios ignoran dónde están los datos. Migrar a SQL o a una base administrada en la nube exige solo otra implementación (Fowler, 2002); además facilita pruebas con dobles.
StrategySeleccionado PoliticaDescuento encapsula la regla del 10 % sobre $200.000; nuevas promociones se agregan como clases nuevas e inyectables sin modificar PedidoService (abierto/cerrado).
Inyección de dependencias (IoC)Seleccionado App compone repositorios → servicios → controladores por constructor: bajo acoplamiento y punto único de composición, versión ligera de un contenedor IoC.
SingletonDescartado Estado global difícil de probar; se logra el efecto (una sola instancia compartida) inyectando el repositorio único desde App.
API Gateway / BFFDiferido Pertinente cuando existan varios microservicios; sobreingeniería para un módulo único. Queda como evolución natural documentada.
Circuit BreakerDiferido Aplica ante dependencias externas que pueden fallar; el prototipo aún no tiene dependencias externas.
CQRSDiferido Útil para escalar lecturas/escrituras por separado en gran volumen; duplicaría esfuerzo a esta escala.
Consideración de nube: el prototipo se empaqueta en Docker (JRE puro), ideal para Azure Container Apps / App Service, que crea pods adicionales ante alta demanda (escalabilidad horizontal) o aumenta recursos del nodo (escalabilidad vertical), tal como se describe en Microsoft (2024).

5. Prototipo funcional

5.1 Tecnología y estructura

Java 26 puro (servidor HTTP integrado com.sun.net.httpserver, sin Maven ni librerías externas), vista SPA con HTML/CSS/JS vanilla y almacenamiento en memoria sembrado con el catálogo. La estructura refleja la arquitectura:

src/cafeexpress/
 ├── controller/   ProductoController, PedidoController      (MVC - Controlador)
 ├── service/      PedidoService, ProductoService,
 │                 PoliticaDescuento + DescuentoPorMonto     (reglas + Strategy)
 ├── repository/   interfaces ProductoRepository/PedidoRepository
 │   └── memory/   EnMemoria...Repository                    (Repositorio)
 ├── domain/       Producto, Pedido, DetallePedido, enums    (Modelo)
 ├── web/          Http, SimpleJson, Estaticos               (infraestructura)
 └── App.java      composición e inyección de dependencias
static/            index.html, styles.css, app.js            (Vista)

5.2 Reglas de negocio evidenciadas

  • Descuento automático del 10 % cuando el subtotal es ≥ $200.000 (verificado: pedido de $220.000 → descuento $22.000 → total $198.000).
  • Pagos con tarjeta solo desde $5.000: pedidos menores son rechazados con HTTP 422 y mensaje claro al usuario.
  • Ciclo de vida con transiciones válidas: pasar de RECIBIDO a ENTREGADO se rechaza; RECIBIDO → EN_PREPARACION se acepta.
  • Operaciones administrativas protegidas: sin token responden HTTP 401.

5.3 Ejecución

# Local (solo JDK):
javac -encoding UTF-8 -d bin (Get-ChildItem -Recurse src -Filter *.java).FullName
java -cp bin cafeexpress.App           # http://localhost:8080

# Contenedor (nube):
docker build -t cafe-express .
docker run -p 8080:8080 cafe-express

Token de administración demostrativo: admin123. En producción se sustituiría por Identity Server (OAuth2/JWT) sin tocar la lógica de negocio, pues la verificación ocurre en un único punto de la capa controlador.

5.4 Evidencia de los patrones en el código

  • Repositorio: PedidoService recibe PedidoRepository (interfaz); la implementación en memoria es reemplazable.
  • Strategy: PoliticaDescuento.calcular(subtotal); cambiar la promoción no modifica el servicio.
  • Inyección de dependencias: todos los colaboradores llegan por constructor desde App.main().
  • MVC: la vista nunca calcula reglas; solo refleja las respuestas del servicio.

6. Conclusiones

  • La separación de responsabilidades (vista, controlador, servicio, repositorio, datos) satisface simultáneamente los requisitos no funcionales: mantenibilidad, extensibilidad y protección de la información.
  • El patrón Repositorio desacopla la persistencia: migrar a base de datos administrada en la nube no exige reescribir la lógica, solo escribir otra implementación.
  • La arquitectura está preparada para crecer: escala verticalmente potenciando el nodo y horizontalmente replicando contenedores idénticos (pods) detrás de un balanceador, sin reconstruir el sistema.
  • Los patrones descartados (Singleton explícito, API Gateway, Circuit Breaker, CQRS) quedan documentados con su criterio de activación, lo que convierte este diseño en una hoja de ruta evolutiva y no en una solución cerrada.
